# 가족 돌봄 서비스 PRD v0.15

갱신: 2026-10-08, Asia/Seoul. 배포 마감: 2026-10-09 07:00.
기준: 사용자의 2026-10-08 최종 답변. 동시 개정: DB v1.3 / API v1.1.
이 문서는 v0.14를 대체하는 현재 제품 계약이다. 문서 개정은 코드·배포 완료를 뜻하지 않는다. 구현 현황과 잔여 작업은 remaining-work-20261008.md를 참조한다.

## 1. 목적과 범위

진료 정보를 가족이 함께 이해하고 건강 일정의 담당자를 정해 돌봄 공백을 줄인다. 가상 진료 데이터로 녹음·전사·OCR·요약·처방 확인·일정 배정·실제 알림을 시연한다. AI는 추출·요약에 사용하고 배정은 서버 규칙으로 결정한다. 진단·치료 추천을 하지 않으며 기록 정확도나 실제 약 섭취를 보장하지 않는다.

회원가입 → 로그인 → 부모 공동체 연결/승인 → 돌봄 일정 캘린더 → 진료 기록·분석 → 확인 필요 처리 → 일정 자동 배정 → 수락/거절·담당 변경 → 수행 완료가 핵심 흐름이다.

| 항목 | 확정 정책 |
|---|---|
| 계정 | 부모/자녀 선택, 전화번호 가입 및 로그인. SMS·비밀번호 없음 |
| 공동체 | 부모 1명당 하나. 계정당 ACTIVE 또는 승인 대기 공동체는 하나 |
| 자녀 역할 | 주돌봄자녀=priority 1, 공동돌봄자녀=priority 2. 다른 순위 없음 |
| 메인 | 돌봄 일정 캘린더. Today 페이지 없음 |
| 개인 일정 | 별도 개인 가능 시간 페이지. 건강 일정·이벤트 표시 없음 |
| 수동 생성 | 건강검진·병원 내용·기타 돌봄의 단건만 가능 |
| 약 복용 | AI 추출 후 처방 확인으로 생성. 수동 추가 불가 |
| 문서 분류 | 처방전·진단서·약봉투만 |
| 미지정 | 담당자 없음은 공통 상태, 해결/미해결은 사용자별 응답 상태 |
| 반복 알림 | 매일 09:00 KST, 본인의 미해결 미지정이 있을 때만. DAILY/ONCE 설정 없음 |

## 2. 가입·로그인·부모 정보

### 2.1 가입과 로그인 분리

- 부모 가입: 전화번호와 부모 선택만 입력한다. 이름·출생연도를 부모 가입 시 요구하지 않는다.
- 자녀 가입: 전화번호·이름과 자녀 선택을 입력한다. 부모 연결은 가입 흐름에서 이어서 진행할 수 있으며 나중에 연결도 가능하다.
- 같은 정규화 전화번호로 중복 가입을 거부한다. 기존 회원은 로그인 화면에서 전화번호만 입력한다. 가입 요청을 기존 계정 로그인으로 바꾸지 않는다.
- 표시 이름이 아직 없는 부모는 화면에 ‘부모 정보 입력 전’으로 표시한다. 가짜 이름을 입력 완료 데이터로 저장하지 않는다.
- 계정 구분은 가입 후 수정하지 않는다. 전화번호 변경/계정 복구/SMS는 이번 범위 밖이다.
- 전화번호는 식별자일 뿐 소유 인증을 하지 않는다. 이번 가상 데이터 시연 계약이며 실제 건강정보 운영용 본인 확인으로 표현하지 않는다.
- 기존 4계정은 회귀 테스트·선택적 시드 자료다. 제품 가입·로그인을 4개의 loginKey에 제한하지 않는다.

### 2.2 인증과 인가

로그인 성공 시 32바이트 난수의 base64url opaque Bearer token을 발급한다. SHA-256 해시만 DB에 저장하고 원문은 응답에만 반환한다. JWT·refresh token·인증 쿠키는 사용하지 않는다. 복수 세션을 허용하고 로그아웃은 현재 세션만 폐기한다. 기본 절대 만료 24시간, 실제 expiresAt이 기준이다.

인증 실패 401, 인증 후 공동체/소유권 위반 403, 없는 리소스 404다. ACTIVE 구성원만 공동체 건강정보를 조회·변경한다. 승인 대기 계정도 로그인·본인 정보·본인 신청 상태/취소는 가능하지만 공동체 진료·일정·파일·구성원·알림은 열람할 수 없다.

### 2.3 부모 정보 최초 입력

부모 가입과 부모 공동체/RECIPIENT 멤버 생성은 원자적이다. 첫 연결 자녀는 어머니/아버지, 성함, 출생연도를 입력하고 주돌봄자녀로 즉시 합류한다. ‘어머니/아버지’는 부모 공통 정보이며 자녀마다 별도로 저장하지 않는다. 출생연도만으로 정확한 만 나이를 표시하지 않고 출생연도를 기본 표시한다.

최초 정보 저장과 첫 자녀 가입은 같은 트랜잭션이다. 동시 요청 중 먼저 성공한 자녀만 첫 연결이고 나머지는 공동돌봄자녀 승인 대기다. 뒤 요청의 부모 정보는 덮어쓰지 않는다. 최초 입력 후 수정 API/화면은 제공하지 않는다. 자녀가 모두 탈퇴했다가 다시 연결되어도 부모 정보를 재입력·변경하지 않는다.

## 3. 공동체 연결·승인·역할·탈퇴

- 자녀는 부모 회원의 전화번호로 연결한다. 부모가 등록되지 않았거나 자녀 번호이면 연결 불가다.
- ACTIVE 자녀가 0명이면 다음 신청자는 주돌봄자녀로 즉시 합류한다. 부모 정보 미입력인 경우에만 최초 정보 입력을 요구한다.
- ACTIVE 자녀가 있으면 신규 신청자는 priority 2 승인 대기다. 현재 ACTIVE 주돌봄자녀 중 한 명의 승인으로 ACTIVE가 된다. 부모·공동돌봄자녀는 승인할 수 없다.
- 주돌봄자녀는 여러 명 가능하다. 역할 변경은 부모를 포함한 모든 ACTIVE 구성원이 할 수 있다. 부모의 RECIPIENT 역할은 자녀 역할로 변경할 수 없다.
- 승인자는 승인 순간에도 ACTIVE 주돌봄자녀여야 한다. 승인/거절/신청 취소 경쟁 중 한 전이만 성공한다.
- 승인 대기 화면에 머물며 앱의 뒤로 가기는 신청 취소 API 성공 후 이전 화면으로 이동한다. 브라우저 종료만으로 취소되지 않는다. 새로고침·재로그인 시 서버의 대기 상태를 복원한다. 취소 실패 시 대기를 유지하고 재시도를 안내한다.
- 거절·취소 후 재신청 가능하다. 신청 이력은 보존한다. 이미 ACTIVE면 중복 가입하지 않는다.
- 마지막 주돌봄자녀가 강등/탈퇴할 때 다른 ACTIVE 자녀가 남는다면 먼저 다른 자녀를 주돌봄자녀로 지정해야 한다. 다른 ACTIVE 자녀가 없으면 탈퇴 가능하다. 대기자만으로 자동 승격하지 않는다. 대기자는 새 신청을 통해 첫 연결 규칙을 다시 평가받을 수 있다.
- 역할 변경은 앞으로의 자동 배정에만 적용하며 기존 담당자를 재배치하지 않는다.
- 자녀 탈퇴는 미래 부적합 배정 해제·미지정 사건 생성·탈퇴자 미발송 알림 차단을 원자 처리한다. 부모의 공동체 탈퇴는 제공하지 않는다.
- 모든 ACTIVE/대기 관계를 합쳐 계정당 하나만 허용한다. 다른 부모에게 연결하려면 기존 가입에서 탈퇴하거나 신청을 취소해야 한다. 과거 LEFT 이력은 보존한다.

## 4. 화면과 캘린더

| 화면 | 주요 동작 |
|---|---|
| 가입/로그인 | 별도 화면, 부모/자녀 가입, 전화번호 로그인 |
| 부모 연결/정보 입력 | 전화번호 조회, 첫 연결 부모 정보 입력, 연결 신청 |
| 승인 대기 | 상태 표시, 뒤로 가기로 신청 취소 |
| 메인: 돌봄 일정 | 월 캘린더, 날짜별 건강 일정 카드, ‘내 일정만 보기’ 필터 하나 |
| 일정 상세/수정 | 상세·완료·재열기·삭제·담당자 선택, 담당자의 인계 |
| 개인 일정 관리 | 활동 시간·근무·날짜별 FULL/PARTIAL/UNAVAILABLE 설정 |
| 진료 기록/상세 | 녹음·문서, AI 요약·근거, 처방/후보 확인 |
| 가족 관리 | 구성원 역할 변경, 주돌봄자녀의 가입 승인·거절 |
| 알림/설정 | 알림함·읽음·브라우저 푸시 권한. 반복 주기 설정 없음 |

### 4.1 날짜와 목록

- 기본은 선택한 KST 날짜에 시작하는 공동체 전체 일정이다. 완료 포함, 취소 제외.
- 미완료 미지정은 상단: 본인 미해결 → 본인 해결 → 나머지 일정. 같은 구간은 startsAt,id 오름차순.
- ‘내 일정만 보기’는 현재 assignee=로그인 사용자만 표시한다. 미지정은 이 필터에서 제외한다. 서버 조회 필터를 사용한다.
- 날짜 표시는 전체 공동체 기준으로 유지한다(구현 기본값). 내 일정 필터는 하단 목록에만 적용하여 다른 가족의 미지정 경고를 숨기지 않는다.
- 일정 없음=회색, 취소 제외 일정 있음=일반 표시, 미완료 미지정 있음=빨간 표시. 사용자 거절 여부와 무관하게 담당자가 없으므로 빨간 표시를 유지한다.
- 만료된 인계 사건 자체만으로 빨간색을 만들지는 않는다. 다만 과거 일정이 여전히 PENDING·미지정이면 그 날짜는 빨간색이고 경과 표시를 함께 한다. 완료/취소 시 해당 미지정 경고는 사라진다.
- 색상 외에 ‘미지정 n건’ 등 텍스트/접근성 라벨을 제공한다.
- 개인 일정 페이지에는 건강 일정 카드·인계/미지정 이벤트·빨간 경고를 표시하지 않는다.

## 5. 건강 일정·배정·수락·거절

### 5.1 유형과 생성 경로

| UI 유형 | API kind | 직접 단건 생성 |
|---|---|---|
| 건강검진 | EXAM | 허용 |
| 약 복용 | MEDICATION | 금지, 처방 확인 흐름만 |
| 병원 내용 | HOSPITAL | 허용 |
| 기타 돌봄 | OTHER | 허용 |

사용자가 직접 만드는 일정은 ONCE 하나다. 수동 반복 생성 및 약 복용 우회 생성은 서버에서도 거부한다. 기존 PICKUP(약 수령)은 OTHER로 이관하고 제목·내용은 보존한다. 녹음/문서에서 추출되는 일반 일정 및 처방의 반복 생성은 유지한다. 기존 반복 일정의 수정·이번만/앞으로 삭제도 유지한다. 수동 ONCE를 반복으로 바꾸는 수정은 허용하지 않는다.

약 복용 시리즈는 동일 시각·반복 패턴 약들을 기간에 맞게 묶고 날짜별 유효 약 snapshot을 남긴다. 약명·용량·횟수·기간의 신규/변경은 사용자 확인 후 적용한다. 의료적 중단과 일정 삭제는 다르다.

### 5.2 자동 배정

ACTIVE 자녀 중 전체 구간 가능·충돌 없음 → priority 1 우선, 없으면 2 → 같은 공동체 KST 주간 미취소 배정 건수 최소(완료 포함) → 4시간 묶음 선호 → member ID로 결정한다. 부모는 자동 배정에서 제외한다. 같은 사람의 미취소 배정은 과거 공동체 이력을 포함해 충돌 검사해 이관 중 남은 미래 일정도 겹치지 않게 한다. 현재 제품에서는 공동체 전환 UI를 제공하지 않는다.

4시간 묶음은 같은 부모·KST 날짜·신규 일정의 첫 시작과 마지막 시작 차이 240분 이내이며 연쇄 묶음을 하지 않는다. 중간 전체 시간 가능·후보 교집합·묶음 전 최소 주간 건수를 검사하고 기존 일정을 재배치하지 않는다. 일정과 완료 단위는 각각 유지한다.

가능 시간 미등록은 후보 제외. FULL은 활동 시간 전체, UNAVAILABLE은 없음, PARTIAL은 근무 제외 또는 명시한 구간이다. 기본 활동 시간은 07:00~22:00, 자정 넘는 근무는 날짜별 분할, 구간은 [start,end), 인접 구간 병합이다.

### 5.3 미지정과 개인 응답

담당자가 없다는 공통 상태와 해당 사용자의 UNRESOLVED/RESOLVED 응답을 분리한다. 실행 상태는 PENDING/COMPLETED/CANCELED이며 ‘해결 미지정’을 완료로 저장하지 않는다.

- 최초 배정 실패: 미지정 사건을 만들고 모든 ACTIVE 구성원에게 미해결로 보인다. 즉시 인계 알림은 없고 09시 대상이 된다.
- 현재 담당자 본인이 ‘다른 가족에게 인계하기’를 누르면 담당 해제+새 사건+즉시 인계 알림을 원자 처리한다. 다른 구성원은 이 버튼으로 대신 해제할 수 없다.
- 가능 시간 축소·시간 수정·탈퇴로 부적합한 담당이 해제되어도 새 사건과 즉시 인계 알림을 만든다. 다른 사람에게 자동 재배정하지 않는다.
- 미해결 카드/상세에서 수락하면 본인 담당으로 지정한다. 가능 시간·충돌·상태를 다시 검사하고 동시 수락은 한 명만 성공한다.
- 거절은 현재 사건에 대한 본인의 응답만 기록한다. 다른 가족에게는 미해결이고 일정은 계속 미지정이다. 같은 거절 재요청은 최초 응답을 유지한다.
- 거절 후 카드에 수락 버튼을 다시 제공하지 않는다. 일정 수정 화면에서 자신을 지정할 수 있다.
- 모든 ACTIVE 구성원은 일정 수정에서 구성원 목록의 체크로 담당자 한 명을 지정/교체할 수 있다. 현재 담당자가 체크되어 있고 다른 사람 선택 시 교체한다. 부모도 수동 지정·수락은 가능 시간 검사 후 가능하다. 체크 해제로 무담당을 만드는 대신 담당자 본인의 인계 동작을 사용한다.
- 누군가 거절했더라도 다른 가족이 그 사람을 수동 지정하는 것은 허용한다. 거절은 배정 금지 설정이 아니며 수동 변경의 공통 검증을 적용한다.
- 수락/수동 지정은 현재 사건을 종료한다. 이후 다시 해제되면 새 사건 ID를 발급하여 이전 거절은 역사로 남고 모든 현재 구성원에게 다시 미해결이 된다. 반복 일정의 다른 날짜도 별도 사건이다.
- 시작 후 아직 끝나지 않은 PENDING 일정의 수락은 기존 종료 전 검사와 전체 가능 구간 검사를 따른다. endsAt<=now이면 수락·거절·담당 변경을 거부하고 시간 수정 또는 결과 기록을 안내한다.

### 5.4 완료·수정·삭제

수행자·완료 처리자·시각을 기록하고 대리 완료·재열기 이력을 보존한다. 완료는 실제 복약 센서 검증이 아니다. 완료·취소는 미지정 사건과 미발송 알림을 종료한다. 재열기 후 부적합/무담당이면 유효 시간 내 새 사건을 만든다.

단건 수정은 anchorDate를 유지한다. 반복 일괄 수정은 미래 미완료만 새 revision에 반영하고 완료·시작한 건을 보존한다. RULE_CHANGED 취소만 명시적 규칙 수정으로 복원하며 USER_ONE/USER_FUTURE는 재생성하지 않는다. 앞으로 삭제는 anchor 경계와 stopFromDate를 유지한다. preview/expectedVersion·멱등·audit 계약을 따른다.

## 6. 진료·문서·AI
### 6.1 녹음과 진료 기록

#### 6.1.1 녹음 흐름

1. 현재 돌봄 대상을 확인하고 마이크 권한을 요청한다.
2. 녹음 시작·종료를 누른다. 화면을 벗어나거나 녹음이 중단되면 사용자에게 알려 복구 가능한 분량만 처리한다.
3. 종료 후 ‘이 녹음을 사용할까요?’에 사용 / 삭제를 제공한다.
4. 사용 시 업로드, 전사, 요약·추출 작업을 비동기로 시작한다. 사용자가 전사 전체를 확인하는 필수 단계를 추가하지 않는다.
5. 진료 상세가 생성되고 가족에게 결과를 공유한다. 자동화 예외는 아래 확인 필요 정책으로 처리한다.

회원가입 동의와 녹음 전 안내는 이 사용 여부 질문과 별개다. 대화 참여자가 자신의 진료 대화를 기록한다는 사용 원칙을 안내한다. 원격으로 다른 사람의 대화를 몰래 녹음하는 기능은 만들지 않는다.

#### 6.1.2 처리 상태와 실패

상태: 업로드 중 → 전사 중 → 요약 중 → 완료 또는 일부 확인 필요. 실패 단계와 재시도 가능 여부를 보관한다.

- 전사 결과를 저장한 뒤 원본 음성을 삭제한다. 요약 실패는 저장된 전사로 재시도한다.
- 전사 실패 음성은 재시도용 임시 보관 후 최대 24시간 내 삭제하는 것을 추천한다. 24시간은 제품 보관 상한 제안이며 법정 기간이 아니다.
- 사용자가 취소·삭제하면 관리하는 임시 복사본과 브라우저 Blob도 해제한다. 서버 삭제 실패는 재시도 작업과 운영 경고로 추적한다.
- 외부 AI 업체 보관분은 별도 정책에 따르므로 ‘모든 곳에서 즉시 삭제’라고 표현하지 않는다.
- 업로드·추출 요청 식별자로 중복 클릭과 작업 재시도에 따른 중복 기록·일정을 막는다.
- 추천 녹음 상한은 20분, 음성 파일 25MB. 실제 선택한 API와 휴대폰에서 확인 후 고정한다.
- 녹음 중 화면 잠금·백그라운드 지속을 보장하지 않는다. iPhone과 Android에서 권한 거부·전화 수신·화면 전환 상황을 확인한다.

#### 6.1.3 진료 상세 데이터

진료일, 의료기관(미상 가능), 작성자, 한눈에 보는 요약, 기록된 증상·검사·설명, 복약 관련 언급, 후속 조치, 원문 근거 구간, 관련 문서, 연결 일정, 처리 상태를 저장한다. 병원명이 없으면 추정하지 않는다. 전사에는 의료진 발언으로 확인되지 않은 내용을 의료진 지시처럼 표시하지 않는다.

### 6.2 문서 관리와 AI 확인 정책

처방전·진단서·약봉투를 사진 또는 PDF로 등록한다. 촬영·파일 선택 후 대상과 진료 연결을 확인하고 서버 validation 통과 후 자동 추출한다. 관련 진료가 없으면 문서 독립 기록으로 저장할 수 있다. 원본은 비공개 저장소에서 Bearer 인증·ACTIVE 공동체 멤버십 인가 후 제공한다.

### 문서 업로드 MVP 정책 — 서비스 자체 확정 제한

| 항목 | 우리 서비스 정책 |
|---|---|
| 지원 형식 | JPG/JPEG (`image/jpeg`), PNG (`image/png`), WEBP (`image/webp`), PDF (`application/pdf`) |
| 파일 크기 | 파일당 최대 **10MB**. 구현 단위는 10,000,000 bytes로 통일하며 해당 크기는 허용, 초과는 거부 |
| PDF | **파일당 최대 10페이지**. 10페이지는 허용, 11페이지 이상은 거부 |
| 이미지 문서 | **한 기록(encounter)당 최대 10장**. 기존 활성 이미지와 새 이미지의 합계로 검사하며 한 요청당 제한으로 오해하지 않음 |
| 초과 시 동작 | 필요한 페이지만 선택하거나 파일을 나누어 재업로드하도록 안내. 이미지 분할 업로드도 같은 기록의 10장 상한을 우회하지 못함 |

이 10MB / PDF 10페이지 / 이미지 10장은 비용·처리 시간·사용자 경험·해커톤 규모를 위한 **제품 정책**이며 OpenAI 하드 제한이 아니다. PDF 페이지를 이미지 업로드 10장과 중복 계산하지 않는다. PDF 파일 개수나 기록 전체 PDF 페이지 합계에 새로운 제품 상한을 임의로 추가하지 않는다. 필요한 페이지 선택·분할은 사용자가 파일을 준비하는 안내이며 새 PDF 편집 기능을 MVP에 추가하는 뜻이 아니다.

작은 약명·숫자·단위가 읽힐 해상도를 유지한다. 프론트에서 일괄적인 저해상도 축소나 과도한 JPEG 압축으로 크기를 맞추지 않는다. 원본을 기본으로 업로드하고 크기 초과는 필요한 영역·페이지를 선택하거나 파일을 나누도록 안내한다. 모델의 detail 옵션은 선택 모델의 공식 지원을 확인하고 작은 글자 샘플로 평가한 후 정한다. 정확도는 보장하지 않으며 기존 원문 대조·확인 필요 정책을 유지한다.

#### 외부 AI 입력 검증

공급자 제한은 선택 모델·endpoint의 최신 공식 문서를 구현 시 확인한다. 제품의 10MB/10페이지/10장 제한과 별도로 외부 요청의 context·크기·형식을 검증한다. 이번 문서 개정은 외부 문서 재검증이 아니다. 실제 OpenAI 검증은 기존 보고 기준 성공이며 모바일 표본 호환과 별개다.

#### 문서 업로드 validation 계약

API v1.1의 공통 오류 envelope와 아래 코드를 사용한다.

| 서버 검증 실패 | HTTP / 오류 코드 | 사용자 동작 |
|---|---|---|
| 실제 형식이 지원하지 않는 MIME | 415 Unsupported Media Type / `UNSUPPORTED_MEDIA_TYPE` | JPG/JPEG·PNG·WEBP·PDF로 준비 |
| 파일 바이트 > 10,000,000 | 413 Payload Too Large / `FILE_TOO_LARGE` | 필요한 페이지만 선택하거나 파일 분할 |
| 실제 PDF > 10페이지 | 422 Unprocessable Content / `PDF_PAGE_LIMIT_EXCEEDED` | 10페이지 이하로 선택·분할 |
| 기록의 기존 활성 이미지 + 신규 이미지 > 10장 | 422 / `IMAGE_COUNT_LIMIT_EXCEEDED` | 불필요한 이미지를 제거하거나 별도 기록으로 정리. 동일 기록에 재요청해도 초과 불가 |
| 빈 파일·손상된 PDF/이미지·유효 페이지가 없는 PDF | 422 / `INVALID_DOCUMENT` | 정상 파일로 다시 업로드 |
| 서버에서 읽을 수 없는 암호화 PDF | 422 / `INVALID_DOCUMENT` | 암호를 해제한 사본으로 다시 업로드. 비밀번호 수집 기능은 추가하지 않음 |

확장자·브라우저 Content-Type·클라이언트 페이지 수를 신뢰하지 않는다. 서버가 실제 bytes, 파일 signature 및 안전한 PDF 파서/이미지 디코더로 형식·읽기 가능 여부·페이지 수를 확인하고 확인된 MIME을 저장한다. 허용 확장자로 바꾼 실행 파일은 거부한다. 프론트 검사는 안내용이고 최종 판정은 서버다.

검증 순서: Bearer 인증·리소스의 ACTIVE 멤버십 인가 → 제한된 크기의 비공개 임시 업로드 → 실제 바이트·MIME·구조·페이지 검사 → 기록 단위 이미지 개수 검사와 소스 등록 → 검증된 입력만 작업 접수 → 외부 요청 직전 모델/요청 전체 제한 재검사 → OpenAI 호출. 거부된 파일은 AVAILABLE이나 처리 대기 소스로 게시하지 않고 임시 파일을 정리한다. 본 제한은 DOCUMENT에 적용하며 기존 AUDIO 제한을 바꾸지 않는다.

OpenAI가 입력 크기·context·이미지 형식/해상도 등 입력 제한으로 거부하면 `processing_job.status=FAILED`, `error_code=AI_INPUT_LIMIT_EXCEEDED`로 기록한다. OCR 소스는 FAILED로 표시하고, ANALYZE 실패는 준비된 OCR 텍스트를 유지한다. 일반 500이나 성공으로 숨기지 않고 작업 조회에서 단계·오류 코드·파일 조정 안내를 반환한다. 입력을 바꾸지 않는 무한 자동 재시도는 하지 않으며 타임아웃·429 같은 일시 실패와 구분한다. 동기 검증 실패의 4xx와 비동기 작업 조회의 정상 HTTP 응답 안에 담긴 FAILED 상태를 구별한다. 원본·토큰·의료 텍스트나 공급자의 민감한 오류 본문을 일반 로그에 복사하지 않는다.

Nginx·Spring multipart의 파일 제한과 전체 요청 제한을 구분한다. 10MB 파일 하나에 multipart overhead가 붙어 정상 업로드가 거부되지 않게 하고, 여러 파일은 합계/overhead를 고려해 전달하거나 순차 업로드한다. 인프라가 먼저 거부한 413도 프론트에서 처리하며 가능한 범위에서 공통 오류 계약과 허용 Origin의 CORS 헤더를 유지한다. 전체 요청 제한을 OpenAI의 PDF 파일 합계 제한과 동일한 의미로 설명하지 않는다.


### 최소 확인 흐름

모든 결과를 한 줄씩 승인하게 하지 않는다. 일반 일정은 필수 정보가 명확하고 원문 근거가 있으면 생성·배정한다. 다만 다음 항목은 ‘확인 필요’로 표시하고 해당 자동 실행만 보류한다.

| 경우 | 동작 |
|---|---|
| 날짜·시간·업무 내용이 명확한 방문·동행·수령 | 일정 생성·배정, 상세에서 언제든 수정 |
| ‘다음 주에’, ‘식후’, ‘나중에 검사’처럼 구체 시각 부족 | 날짜/시간을 채울 한 카드 표시, 배정·시각 알림 보류 |
| 약명·용량·횟수·복용 기간의 신규 또는 변경 | 같은 진료의 신규·변경 복약 항목을 한 화면에 모아 ‘맞아요’ 한 번으로 확인 후 활성화. 매 복용 때 다시 확인하지 않음 |
| OCR과 음성 내용의 불일치 | 어느 쪽도 자동 우선하지 않고 충돌 항목 확인 요청 |
| 불필요한 문장·조건부 계획·중단 지시 | 실행 일정으로 무조건 만들지 않음. 필요 시 확인 후보로 제시 |
| 이미 동일한 진료·약·날짜의 일정 존재 | 중복 후보 안내, 재처리 시 기존 발생 건 유지 |

확인 화면은 별도 검토 절차를 여러 단계로 만들지 않고 진료 상세의 ‘확인할 내용’ 영역 하나로 통합한다. 녹음 사용 확인을 누르면 요약까지 자동 처리하며, 확인할 내용이 있을 때만 해당 영역을 표시한다.

- 상단에 필요한 질문만 표시한다. 예: ‘A약: 하루 2회, 1회 1정으로 기록했어요. 맞나요?’ 이는 가상 UI 문구 예시이며 복약 지시가 아니다.
- 명확하게 읽힌 신규·변경 복약 항목이 여러 개면 한 목록으로 묶고 ‘맞아요’ 한 번으로 확인한다. 약마다 별도 팝업을 띄우지 않는다. 필요한 원문은 ‘원문 보기’에서 펼친다.
- 정보가 누락되면 해당 입력만 보여준다. 예: ‘병원에 몇 시까지 가면 되나요?’ → 시간 선택 → 확인. 날짜·시간을 임의로 채우지 않는다.
- 서로 다른 자료가 충돌하면 어느 쪽인지 선택하거나 직접 수정하게 한다. 미해결 충돌은 일괄 ‘맞아요’로 통과시키지 않는다.
- 기본 버튼은 ‘맞아요 / 수정’. ‘나중에’로 닫을 수 있고, 해당 항목만 확인 필요 상태로 남는다. 원문도 불명확하면 확인 전까지 배정하지 않는다.
- ‘맞아요’는 사용자의 내용 확인 기록이며 의료진 검증을 뜻하지 않는다. 가족 중 한 명이 확인하면 공동체 전체에 반영되며 확인자·시각을 남긴다.
- 이미 확인된 동일 처방은 매일 재확인하지 않는다. 확인된 핵심 약 정보가 바뀌거나 새 충돌이 생길 때만 다시 표시한다.
- 일반적인 명확한 일정에는 확인 팝업을 띄우지 않는다. 문서와 녹음을 함께 등록해도 같은 진료의 중복 질문은 합친다.

위 검사는 오류를 완전히 잡는 장치가 아니다. 원문 존재·형식 검증·소스 비교는 모델의 자체 확신 점수만 사용하는 것보다 검토 근거를 남기기 위한 설계다. 기록·일정에서 수정 및 삭제가 가능해야 한다. 확인 필요 알림은 09시 미지정 알림과 별개로 보낸다.

약 변경은 기존 반복 일정을 조용히 덮어쓰지 않는다. 적용 시작일과 대상 처방을 확인한 뒤 미래 발생분만 변경하며 완료 이력은 유지한다. 음성·문서 자체에도 잘못 읽히거나 모호한 내용이 있을 수 있어 두 입력이 존재한다는 사실만으로 검증 완료로 보지 않는다.


문서마다 documentType=PRESCRIPTION(처방전), DIAGNOSIS(진단서), MEDICINE_BAG(약봉투)를 업로드 시 선택한다. AUDIO에는 null이다. 기존 분류 없는 문서는 자동 추측하지 않고 이관 목록에서 확인하며, 확인 전 LEGACY_UNCLASSIFIED로만 반환하고 신규 업로드에는 허용하지 않는다.

현재 실검증 음성은 RIFF/WAVE PCM, 25,000,000 bytes·1200초 상한이다. 모바일에서 생성한 WebM/MP4를 확장자만 바꿔 업로드하지 않는다. 추가 형식은 실기기 표본 검증 후 반영한다.

## 7. 알림

- 실제 Web Push와 알림함을 분리한다. 권한 거부·푸시 실패라도 알림함은 생성한다.
- 담당자가 내려놓거나 자동 해제된 사건은 현재 ACTIVE 구성원에게 즉시 인계 안내한다. 최초 NO_CANDIDATE에는 즉시 인계 알림이 없다.
- 매일 09:00 KST 각 ACTIVE 구성원에 대해 미래(startsAt>now) PENDING·미지정·현재 OPEN 사건 중 본인 거절 없는 건을 모아 하나의 digest를 만든다. 0건이면 생성·발송하지 않는다. 부모도 포함한다.
- 이전 문서의 DAILY/ONCE와 당일 최초 안내 항목 제외 규칙을 제거한다. 즉시 알림이 있었더라도 09시 현재 본인 미해결이면 digest 대상이다. eventKey=(group,user,KSTdate)로 같은 날짜 정기 알림 중복만 막는다.
- 전송 직전 멤버십·현재 사건 ID·담당자·실행/시간 상태·사용자 거절을 다시 조회한다. 모두 해결/거절/배정/취소되면 취소한다. 이미 표시된 외부 알림을 회수한다고 보장하지 않는다.
- 한 명의 거절은 다른 사람의 digest를 취소하지 않는다. 수락 또는 담당 지정은 모든 사람의 해당 미지정 반복 알림을 종료한다.
- 시작 30분 전/시작 시각 알림과 진료 준비·확인 필요 알림은 별도 유지한다. 지난 예약 시각을 몰아서 발송하지 않는다. 경과 안내는 사건별 1회이며 다음 09시 미래 digest에서는 제외한다.
- 가입 요청/결과는 승인 목록과 본인 신청 상태 조회로 확인한다. 대기자에게 공동체 건강정보 알림을 노출하지 않는다. 가입 전용 푸시는 이번 필수 범위에 추가하지 않는다.
- 잠금화면에는 notificationId/eventId·일반 title/body만 보낸다. 약명·진단명·토큰 없음. provider 수락=SENT이며 표시·읽음과 별개다. tag=eventId. 클릭 후 인증 API로 재조회한다.
- 로그아웃/계정 전환은 현재 기기 구독 해제 → 브라우저 unsubscribe → 세션/Blob/메모리 정리. 다른 기기 이력은 유지한다.

## 8. 구현·배포·보관

프론트 https://knowone-eight.vercel.app / API https://api.gaebalmani.shop. CORS Origin은 끝 슬래시 없는 프론트 Origin이다. Spring Boot+PostgreSQL, 비공개 파일 볼륨, Nginx HTTPS, DB outbox·작업 워커를 사용한다.

외부 AI/푸시는 DB 잠금 밖에서 실행한다. 짧은 claim·lease 회수·fencing으로 이전 worker 결과를 막는다. 일정/멤버 변경은 schedule_guard를 먼저 잠그고 업무·audit·outbox·멱등 성공을 원자 반영한다. 서버 Clock은 주입하고 모든 날짜 경계를 KST로 계산한다.

문서 접근은 Bearer fetch→Blob, 종료 시 revokeObjectURL이다. 건강 응답·원문·토큰은 Service Worker/Cache Storage/IndexedDB 오프라인 캐시에 저장하지 않는다. 음성은 전사 저장 후 삭제하며 실패 음성도 24시간 내 만료·삭제 재시도한다. 기록 삭제는 소스·텍스트·근거·후보를 파기하고 공유 약 업무는 남은 근거에 맞게 보존한다. 백업·외부 AI 업체 보관까지 즉시 삭제라고 표현하지 않는다.

가입/로그인 무인증 전화번호 모드는 해커톤 시연 설정으로 제어하되 prod에서도 명시적으로 켤 수 있다. 배포 프로필명만으로 이 기능을 금지하지 않는다. 실제 환자 기록을 받는 운영은 범위 밖이다. 설정값/secret은 서버에만 저장한다.

## 9. 수용 기준과 문서 결정

1. 부모 전화번호만 가입, 자녀 이름 필수, 중복 번호 가입 실패, 기존 번호 로그인 성공.
2. 첫 자녀 동시 연결에서 정확히 1명 priority 1 ACTIVE, 나머지 priority 2 PENDING.
3. ACTIVE+PENDING 단일 공동체 제약, 승인 전 의료정보 403, 승인/취소 경쟁 한 번만 성공.
4. 모두 역할 변경 가능하지만 마지막 주돌봄자녀 규칙 유지, 부모 정보 최초 저장 후 변경 불가.
5. 개인 거절 A만 RESOLVED이고 B는 UNRESOLVED, 거절은 공동체 업무 완료로 저장되지 않음.
6. 수락/수동 지정 경쟁 한 명 담당, 재해제 새 사건에서 이전 거절 미적용.
7. 09시 개인별 미해결만 전송, 모두 거절한 사람 0건, DAILY/ONCE 및 당일 안내 제외 없음.
8. 수동 약/반복 생성 거부, AI 처방 확인·기존 반복 수정 유지.
9. 메인 날짜/상단 정렬/내 일정 필터/전체 캘린더 경고, 개인 가능 시간에는 건강 이벤트 없음.
10. 문서 세 분류와 파일 parser 제한, 기존 미분류 자료의 명시적 이관.

날짜별 포함은 시작 날짜, 필터는 하단 목록만, 출생연도 허용 범위(1900~현재 KST 연도), 가입 후 로그인 화면 이동, 부모 공통 정보의 미입력 nullable 표현은 문서 정합성을 위한 구현 기본값이다. 사용자가 추가 화면을 확정하면 관련 DTO/UI만 함께 조정한다.
