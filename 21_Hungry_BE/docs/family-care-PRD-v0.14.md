# 가족 돌봄 서비스 PRD v0.14

작성: 2026-10-02 / 배포 마감: 2026-10-09 07:00, Asia/Seoul

상태: 2026-10-02 추가 답변 반영. 가상 진료 데이터 시연용 배포로 확정. 사용자 확정 요구사항과 구현 추천안을 합친 개발 초안. 서비스명은 ‘가족 돌봄 서비스’로 임시 확정한다. ‘추천 기본값’은 사용자 확정 사항과 구별하며 개발 착수 시 조정할 수 있다.

## 1. 목적과 핵심 경험

진료실에서 나온 정보를 가족이 함께 이해하고, 필요한 돌봄 업무를 누가 수행할지 정해 담당자 없는 일정이 방치되지 않도록 한다. 메모닥 기획의 진료 녹음·요약, 문서 인식, 가족 공유, 할 일 추출을 기반으로 가족별 가능 시간, 공동 우선순위, 인계 기능을 구체화한다.

핵심 흐름: 공동체 선택 → 진료 녹음 → ‘이 녹음을 사용할까요?’ → 전사·요약·할 일 추출 → 배정 가능한 일정 자동 배정 → 가족 공유 → 수행 완료 또는 인계 요청.

AI는 정보 추출과 쉬운 요약에 사용한다. 담당자 배정은 서버의 결정적 규칙으로 수행하며 AI 배정 이유 설명은 만들지 않는다. AI의 진단·치료 추천과 누락 없는 기록을 보장하지 않는다.

지역 연결 가설: 월계1동에서 가족과 떨어져 생활하는 어르신과 가족의 정보 전달·돌봄 조율 문제에 적용한다. 해당 지역의 실제 수요·공백 규모는 아직 검증된 사실로 쓰지 않고 현장 인터뷰로 확인한다.

## 3. 사용자·권한·공동체

- 어르신도 기록, 문서 등록, 일정 확인·완료 기능을 사용한다. 화면을 역할별로 분리하지 않는다.
- 가족 모두 공동체의 일정, 담당자, 우선순위를 변경할 수 있다. 변경자·시각·이전 값·새 값을 남긴다.
- 돌봄 대상 본인은 기본 자동 배정 후보에서 제외한다. 본인의 복약 체크는 할 수 있지만 가족 돌봄 업무가 본인에게 배정되지 않게 한다. 이는 추천 기본값이다.
- 이름·전화번호는 계정 필드로 먼저 마련한다. 정식 가입 전에도 서버가 인증한 시연 세션으로 사용자 식별과 공동체 접근 검사를 수행한다.
- 전화번호가 없거나 대상을 찾지 못하면 등록되지 않은 사용자로 안내한다. 같은 공동체 재가입은 중복 멤버십을 만들지 않는다.
- 다중 공동체 전환 시 현재 대상 이름을 녹음·문서·일정 화면 상단에 항상 표시한다.
- 탈퇴 시 이후 접근·푸시 구독 연결을 해제하고, 미래 담당 일정은 담당자 없음으로 전환한다. 혼자 남은 돌봄 대상의 공동체를 자동 삭제하지 않는다.

### 가입과 실제 개인정보의 경계

전화번호·이름 확인만으로 즉시 합류하는 UX는 사용자 요청대로 시연에 반영한다. 다만 이 흐름을 실제 건강정보에 대한 접근 통제로 충분하다고 간주하지 않는다. 공개 시연 데이터는 가상 데이터로 구성한다. 실제 대상자의 데이터 운영 전에는 본인 식별, 정보 공유 동의와 접근 통제 방식을 확정해야 한다.

후속 고유번호는 공개 사용자 식별자가 아니라 비밀 초대 코드로 설계한다. 추측하기 어려운 난수, 만료, 폐기·재발급, 시도 제한을 적용하고 코드로 합류한 사용자 이력을 표시한다. 코드를 안다는 사실과 건강정보 처리·공유 동의는 서로 다른 문제다.

### 인증·인가 공통 계약 — 확정

MVP는 사전 등록 계정 4개(돌봄 대상 1명, 자녀 3명)를 선택해 로그인한다. 서버가 암호학적으로 안전한 난수 생성기로 256bit 수준의 **opaque access token**을 생성한다. JWT를 사용하지 않으며 토큰 자체에는 사용자·권한 정보를 넣지 않는다. 로그인마다 별도의 auth_session을 생성해 사용자별 복수 기기·세션을 허용한다.

로그인 흐름: 계정 선택 → 랜덤 토큰 생성 → 토큰의 SHA-256 hash만 auth_session.token_hash에 저장 → 로그인 응답 본문에 access token 반환 → 프론트가 인증 API 요청마다 `Authorization: Bearer <access-token>` 헤더 전송. 인증용 Cookie나 Set-Cookie는 사용하지 않는다. 원문 토큰을 DB·로그·URL·분석 도구에 남기지 않는다.

서버 검증 흐름: Authorization의 Bearer 토큰 추출 → SHA-256 계산 → auth_session.token_hash 조회 → 세션 존재, `expires_at > 현재 서버 시각`, `revoked_at IS NULL`, 사용자 계정 ACTIVE 확인 → 로그인 사용자 식별 → 요청 리소스 인가. SHA-256은 전달받은 토큰 문자열의 UTF-8 바이트에 적용하며 발급·조회에서 같은 직렬화를 사용한다. 원문 토큰의 인코딩은 구현 때 고정한다.

| 상황 | HTTP 계약 |
|---|---|
| 토큰 없음·잘못된 토큰·만료·revoked 세션 또는 비활성 계정 | 401 Unauthorized |
| 인증 성공 후 다른 care_group 리소스 접근, LEFT 멤버, 허용되지 않은 수정 | 403 Forbidden |
| 정상 인증·인가 | 해당 API의 정상 응답 |

로그아웃은 **현재 토큰에 해당하는 auth_session.revoked_at을 기록**해 이후 사용을 차단하고 프론트의 원문 토큰도 제거한다. 다른 기기의 세션은 유지한다. expires_at은 절대 만료 시각이며 last_seen_at 갱신으로 자동 연장하지 않는다. 세션 수명 24시간은 기존 추천 기본값/설정값으로 유지한다. refresh token·OAuth·새 인증 테이블은 이번 변경에 추가하지 않는다. 만료 시 프론트는 계정 선택 로그인으로 돌아간다.

여기서 ‘문서 권한 확인’은 매번 휴대폰 본인인증·PASS 인증을 하는 의미가 아니다. **인증(Authentication)**은 Bearer Token으로 현재 사용자를 확인하고, **인가(Authorization)**는 해당 데이터가 속한 care_group의 ACTIVE 멤버인지 확인한다. 같은 공동체의 ACTIVE 구성원은 건강 기록을 열람할 수 있으며, 가족별 세부 문서 열람 권한은 MVP에 추가하지 않는다. 기존 업무별 변경 조건·상태·역할 검사는 그대로 적용한다.

예시 계약 `GET /api/documents/{documentId}`(최종 경로는 API 명세에서 고정): token → user 식별 → 문서와 연결 파일에서 실제 care_group 식별 → `(group_id, user_id)`의 ACTIVE 멤버십 검사 → 허용 시 반환, 권한 없으면 403. 클라이언트가 보낸 groupId를 신뢰하거나 UUID 난수성을 접근 제어로 사용하지 않는다.

동일한 경계 검사를 진료 기록·전사·진료 요약·문서 메타/원본 파일·처방 정보·일정·인계·알림·공동체 정보 및 하위 작업 상태 조회에 적용한다. 알림함 항목은 공동체 ACTIVE 검사에 더해 notification.user_id가 로그인 사용자와 일치해야 한다. 개인 가능 시간·푸시 구독·개인 설정은 기존 사용자 소유권 검사를 유지한다. 목록·수정·삭제·일괄 요청도 각각 서버에서 검사하며, 파일은 비공개 저장소에서 검사 후 제공한다. 파일에 브라우저가 Authorization 헤더를 붙일 수 있도록 인증된 fetch로 내려받아 Blob으로 표시하는 방식을 MVP 구현 추천안으로 둔다. 토큰을 파일 URL 쿼리에 넣지 않는다. 로그아웃·계정 전환 시 기존 건강정보 화면·메모리 데이터와 파일 Blob을 해제한다.

### 브라우저 토큰 보관 — 미정과 추천 구분

Bearer 방식 자체는 확정이지만 브라우저 저장 위치는 최종 확정하지 않았다. localStorage는 **가상 의료 데이터 기반 해커톤 MVP 구현 기본값/추천안**으로 사용할 수 있다. 이는 실서비스 보안 정책의 확정사항이 아니다. XSS 발생 시 JavaScript가 접근 가능한 토큰이 탈취될 수 있으므로 실제 건강정보 운영 전 인증·저장 구조와 XSS 방어를 재검토한다. 이번 문서에서는 새로운 인증 기능을 추가하지 않는다. API 응답·토큰·의료 문서를 PWA 오프라인 캐시에 저장하지 않고 로그인 응답에는 `Cache-Control: no-store`를 적용하는 구현 기준을 둔다.

## 5. 녹음과 진료 기록

### 5.1 녹음 흐름

1. 현재 돌봄 대상을 확인하고 마이크 권한을 요청한다.
2. 녹음 시작·종료를 누른다. 화면을 벗어나거나 녹음이 중단되면 사용자에게 알려 복구 가능한 분량만 처리한다.
3. 종료 후 ‘이 녹음을 사용할까요?’에 사용 / 삭제를 제공한다.
4. 사용 시 업로드, 전사, 요약·추출 작업을 비동기로 시작한다. 사용자가 전사 전체를 확인하는 필수 단계를 추가하지 않는다.
5. 진료 상세가 생성되고 가족에게 결과를 공유한다. 자동화 예외는 아래 확인 필요 정책으로 처리한다.

회원가입 동의와 녹음 전 안내는 이 사용 여부 질문과 별개다. 대화 참여자가 자신의 진료 대화를 기록한다는 사용 원칙을 안내한다. 원격으로 다른 사람의 대화를 몰래 녹음하는 기능은 만들지 않는다.

### 5.2 처리 상태와 실패

상태: 업로드 중 → 전사 중 → 요약 중 → 완료 또는 일부 확인 필요. 실패 단계와 재시도 가능 여부를 보관한다.

- 전사 결과를 저장한 뒤 원본 음성을 삭제한다. 요약 실패는 저장된 전사로 재시도한다.
- 전사 실패 음성은 재시도용 임시 보관 후 최대 24시간 내 삭제하는 것을 추천한다. 24시간은 제품 보관 상한 제안이며 법정 기간이 아니다.
- 사용자가 취소·삭제하면 관리하는 임시 복사본과 브라우저 Blob도 해제한다. 서버 삭제 실패는 재시도 작업과 운영 경고로 추적한다.
- 외부 AI 업체 보관분은 별도 정책에 따르므로 ‘모든 곳에서 즉시 삭제’라고 표현하지 않는다.
- 업로드·추출 요청 식별자로 중복 클릭과 작업 재시도에 따른 중복 기록·일정을 막는다.
- 추천 녹음 상한은 20분, 음성 파일 25MB. 실제 선택한 API와 휴대폰에서 확인 후 고정한다.
- 녹음 중 화면 잠금·백그라운드 지속을 보장하지 않는다. iPhone과 Android에서 권한 거부·전화 수신·화면 전환 상황을 확인한다.

### 5.3 진료 상세 데이터

진료일, 의료기관(미상 가능), 작성자, 한눈에 보는 요약, 기록된 증상·검사·설명, 복약 관련 언급, 후속 조치, 원문 근거 구간, 관련 문서, 연결 일정, 처리 상태를 저장한다. 병원명이 없으면 추정하지 않는다. 전사에는 의료진 발언으로 확인되지 않은 내용을 의료진 지시처럼 표시하지 않는다.

## 6. 문서 관리와 AI 확인 정책

처방전·진단서·약 봉투·검사 안내를 사진 또는 PDF로 등록한다. 촬영·파일 선택 후 대상과 진료 연결을 확인하고 서버 validation 통과 후 자동 추출한다. 관련 진료가 없으면 문서 독립 기록으로 저장할 수 있다. 원본은 비공개 저장소에서 Bearer 인증·ACTIVE 공동체 멤버십 인가 후 제공한다.

### 문서 업로드 MVP 정책 — 서비스 자체 확정 제한

| 항목 | 우리 서비스 정책 |
|---|---|
| 지원 형식 | JPG/JPEG (`image/jpeg`), PNG (`image/png`), WEBP (`image/webp`), PDF (`application/pdf`) |
| 파일 크기 | 파일당 최대 **10MB**. 구현 단위는 10,000,000 bytes로 통일하며 해당 크기는 허용, 초과는 거부 |
| PDF | **파일당 최대 10페이지**. 10페이지는 허용, 11페이지 이상은 거부 |
| 이미지 문서 | **한 기록(encounter)당 최대 10장**. 기존 활성 이미지와 새 이미지의 합계로 검사하며 한 요청당 제한으로 오해하지 않음 |
| 초과 시 동작 | 필요한 페이지만 선택하거나 파일을 나누어 재업로드하도록 안내. 이미지 분할 업로드도 같은 기록의 10장 상한을 우회하지 못함 |

이 10MB / PDF 10페이지 / 이미지 10장은 비용·처리 시간·사용자 경험·해커톤 규모를 위한 **제품 정책**이며 OpenAI 하드 제한이 아니다. PDF 페이지를 이미지 업로드 10장과 중복 계산하지 않는다. PDF 파일 개수나 기록 전체 PDF 페이지 합계에 새로운 제품 상한을 임의로 추가하지 않는다. 필요한 페이지 선택·분할은 사용자가 파일을 준비하는 안내이며 새 PDF 편집 기능을 MVP에 추가하는 뜻이 아니다.

작은 약명·숫자·단위가 읽힐 해상도를 유지한다. 프론트에서 일괄적인 저해상도 축소나 과도한 JPEG 압축으로 크기를 맞추지 않는다. 원본을 기본으로 업로드하고 크기 초과는 필요한 영역·페이지를 선택하거나 파일을 나누도록 안내한다. 모델의 detail 옵션은 선택 모델의 공식 지원을 확인하고 작은 글자 샘플로 평가한 후 정한다. 정확도는 보장하지 않으며 기존 원문 대조·확인 필요 정책을 유지한다.

### OpenAI API 기술 제한 — 공식 근거

| 입력 경로 | 공식 문서에서 확인한 기준 |
|---|---|
| PDF `input_file` | 파일 각각 **50MB 미만**, 한 요청 내 파일 합계 **50MB 제한** |
| PDF 페이지 | 위 가이드에 고정된 5페이지·10페이지 상한은 명시되어 있지 않음. 무제한 처리를 보장하는 뜻은 아니며 모델 context·토큰·처리량 제약을 별도로 확인 |
| PDF 처리 | Vision 가능 모델은 추출 텍스트와 페이지 이미지를 함께 입력받으므로 많은 페이지는 토큰·비용·처리 부담을 늘릴 수 있음 |
| Vision 이미지 형식 | JPEG, PNG, WEBP, 비애니메이션 GIF. GIF는 공식 지원 여부와 별개로 우리 MVP에서 제외 |
| Vision 요청량 | 확인 시점 가이드: 요청 payload 최대 512MB, 이미지 최대 1,500개. PDF `input_file`의 50MB 파일 합계와 별개의 입력 기준 |

지원 모델·context·이미지 해상도/patch·detail별 제약도 적용된다. 업로드가 통과해도 AI 입력이 항상 통과하거나 정확히 인식된다고 보장하지 않는다. Files API의 저장용 업로드 허용량을 모델 입력 허용량으로 대신 사용하지 않는다.

공식 문서 확인일: **2026-10-02 (Asia/Seoul)**. 외부 제한은 변경될 수 있으므로 모델·API를 정할 때와 배포 전에 다시 확인한다.

- OpenAI [File inputs](https://developers.openai.com/api/docs/guides/file-inputs): PDF `input_file` 크기·페이지 처리 기준.
- OpenAI [Images and vision](https://developers.openai.com/api/docs/guides/images-vision): Vision 형식·요청량·모델별 입력 및 detail 기준.

### 문서 업로드 validation 계약 — 향후 API 명세 반영

전체 API를 새로 정의하지 않고 기존 오류 코드 규칙(대문자 snake_case)과 인증 401 / 인가 403 계약에 아래 항목을 추가한다. 공통 오류 본문 형식·최종 업로드 경로는 별도 API 명세에서 고정한다.

| 서버 검증 실패 | HTTP / 오류 코드 | 사용자 동작 |
|---|---|---|
| 실제 형식이 지원하지 않는 MIME | 415 Unsupported Media Type / `UNSUPPORTED_MEDIA_TYPE` | JPG/JPEG·PNG·WEBP·PDF로 준비 |
| 파일 바이트 > 10,000,000 | 413 Payload Too Large / `FILE_TOO_LARGE` | 필요한 페이지만 선택하거나 파일 분할 |
| 실제 PDF > 10페이지 | 422 Unprocessable Content / `PDF_PAGE_LIMIT_EXCEEDED` | 10페이지 이하로 선택·분할 |
| 기록의 기존 활성 이미지 + 신규 이미지 > 10장 | 422 / `DOCUMENT_IMAGE_LIMIT_EXCEEDED` | 불필요한 이미지를 제거하거나 별도 기록으로 정리. 동일 기록에 재요청해도 초과 불가 |
| 빈 파일·손상된 PDF/이미지·유효 페이지가 없는 PDF | 422 / `INVALID_DOCUMENT_FILE` | 정상 파일로 다시 업로드 |
| 서버에서 읽을 수 없는 암호화 PDF | 422 / `DOCUMENT_NOT_READABLE` | 암호를 해제한 사본으로 다시 업로드. 비밀번호 수집 기능은 추가하지 않음 |

확장자·브라우저 Content-Type·클라이언트 페이지 수를 신뢰하지 않는다. 서버가 실제 bytes, 파일 signature 및 안전한 PDF 파서/이미지 디코더로 형식·읽기 가능 여부·페이지 수를 확인하고 확인된 MIME을 저장한다. 허용 확장자로 바꾼 실행 파일은 거부한다. 프론트 검사는 안내용이고 최종 판정은 서버다.

검증 순서: Bearer 인증·리소스의 ACTIVE 멤버십 인가 → 제한된 크기의 비공개 임시 업로드 → 실제 바이트·MIME·구조·페이지 검사 → 기록 단위 이미지 개수 검사와 소스 등록 → 검증된 입력만 작업 접수 → 외부 요청 직전 모델/요청 전체 제한 재검사 → OpenAI 호출. 거부된 파일은 AVAILABLE이나 처리 대기 소스로 게시하지 않고 임시 파일을 정리한다. 본 제한은 DOCUMENT에 적용하며 기존 AUDIO 제한을 바꾸지 않는다.

OpenAI가 입력 크기·context·이미지 형식/해상도 등 입력 제한으로 거부하면 `processing_job.status=FAILED`, `error_code=AI_INPUT_LIMIT_EXCEEDED`로 기록한다. OCR 소스는 FAILED로 표시하고, ANALYZE 실패는 준비된 OCR 텍스트를 유지한다. 일반 500이나 성공으로 숨기지 않고 작업 조회에서 단계·오류 코드·파일 조정 안내를 반환한다. 입력을 바꾸지 않는 무한 자동 재시도는 하지 않으며 타임아웃·429 같은 일시 실패와 구분한다. 동기 검증 실패의 4xx와 비동기 작업 조회의 정상 HTTP 응답 안에 담긴 FAILED 상태를 구별한다. 원본·토큰·의료 텍스트나 공급자의 민감한 오류 본문을 일반 로그에 복사하지 않는다.

Nginx·Spring multipart의 파일 제한과 전체 요청 제한을 구분한다. 10MB 파일 하나에 multipart overhead가 붙어 정상 업로드가 거부되지 않게 하고, 여러 파일은 합계/overhead를 고려해 전달하거나 순차 업로드한다. 인프라가 먼저 거부한 413도 프론트에서 처리하며 가능한 범위에서 공통 오류 계약과 허용 Origin의 CORS 헤더를 유지한다. 전체 요청 제한을 OpenAI의 PDF 파일 합계 제한과 동일한 의미로 설명하지 않는다.


### 최소 확인 흐름

모든 결과를 한 줄씩 승인하게 하지 않는다. 일반 일정은 필수 정보가 명확하고 원문 근거가 있으면 생성·배정한다. 다만 다음 항목은 ‘확인 필요’로 표시하고 해당 자동 실행만 보류한다.

| 경우 | 동작 |
|---|---|
| 날짜·시간·업무 내용이 명확한 방문·동행·수령 | 일정 생성·배정, 상세에서 언제든 수정 |
| ‘다음 주에’, ‘식후’, ‘나중에 검사’처럼 구체 시각 부족 | 날짜/시간을 채울 한 카드 표시, 배정·시각 알림 보류 |
| 약명·용량·횟수·복용 기간의 신규 또는 변경 | 같은 진료의 신규·변경 복약 항목을 한 화면에 모아 ‘맞아요’ 한 번으로 확인 후 활성화. 매 복용 때 다시 확인하지 않음 |
| OCR과 음성 내용의 불일치 | 어느 쪽도 자동 우선하지 않고 충돌 항목 확인 요청 |
| 불필요한 문장·조건부 계획·중단 지시 | 실행 일정으로 무조건 만들지 않음. 필요 시 확인 후보로 제시 |
| 이미 동일한 진료·약·날짜의 일정 존재 | 중복 후보 안내, 재처리 시 기존 발생 건 유지 |

확인 화면은 별도 검토 절차를 여러 단계로 만들지 않고 진료 상세의 ‘확인할 내용’ 영역 하나로 통합한다. 녹음 사용 확인을 누르면 요약까지 자동 처리하며, 확인할 내용이 있을 때만 해당 영역을 표시한다.

- 상단에 필요한 질문만 표시한다. 예: ‘A약: 하루 2회, 1회 1정으로 기록했어요. 맞나요?’ 이는 가상 UI 문구 예시이며 복약 지시가 아니다.
- 명확하게 읽힌 신규·변경 복약 항목이 여러 개면 한 목록으로 묶고 ‘맞아요’ 한 번으로 확인한다. 약마다 별도 팝업을 띄우지 않는다. 필요한 원문은 ‘원문 보기’에서 펼친다.
- 정보가 누락되면 해당 입력만 보여준다. 예: ‘병원에 몇 시까지 가면 되나요?’ → 시간 선택 → 확인. 날짜·시간을 임의로 채우지 않는다.
- 서로 다른 자료가 충돌하면 어느 쪽인지 선택하거나 직접 수정하게 한다. 미해결 충돌은 일괄 ‘맞아요’로 통과시키지 않는다.
- 기본 버튼은 ‘맞아요 / 수정’. ‘나중에’로 닫을 수 있고, 해당 항목만 확인 필요 상태로 남는다. 원문도 불명확하면 확인 전까지 배정하지 않는다.
- ‘맞아요’는 사용자의 내용 확인 기록이며 의료진 검증을 뜻하지 않는다. 가족 중 한 명이 확인하면 공동체 전체에 반영되며 확인자·시각을 남긴다.
- 이미 확인된 동일 처방은 매일 재확인하지 않는다. 확인된 핵심 약 정보가 바뀌거나 새 충돌이 생길 때만 다시 표시한다.
- 일반적인 명확한 일정에는 확인 팝업을 띄우지 않는다. 문서와 녹음을 함께 등록해도 같은 진료의 중복 질문은 합친다.

위 검사는 오류를 완전히 잡는 장치가 아니다. 원문 존재·형식 검증·소스 비교는 모델의 자체 확신 점수만 사용하는 것보다 검토 근거를 남기기 위한 설계다. 기록·일정에서 수정 및 삭제가 가능해야 한다. 확인 필요 알림은 사용자별 인계 알림 설정과 분리한다.

약 변경은 기존 반복 일정을 조용히 덮어쓰지 않는다. 적용 시작일과 대상 처방을 확인한 뒤 미래 발생분만 변경하며 완료 이력은 유지한다. 음성·문서 자체에도 잘못 읽히거나 모호한 내용이 있을 수 있어 두 입력이 존재한다는 사실만으로 검증 완료로 보지 않는다.

## 7. 건강 일정과 완료

업무 유형: 복약 도움, 병원 동행, 검사 동행, 약 수령, 기타 직접 추가 업무. 복약 업무는 ‘복약 챙기기’ 하나로 통합한다. 직접 돕거나 연락해 확인할지는 가족이 정하며, UI·DB·AI 추출에 수행 방식 구분을 두지 않는다.

완료 버튼은 공통이다. 담당자의 완료는 ‘해당 돌봄 업무를 수행했다’는 의미이며 실제 약 섭취가 센서로 검증됐다는 의미가 아니다. 수행자·처리자·시각을 기록하고 다른 가족의 대리 완료는 그 사실을 남긴다. 재열기는 변경 이력과 함께 지원한다.

일정 필드: 대상, 제목, 유형, 시작·종료 시각, 기한, 반복, 담당자, 원문 참조, 상태, 생성 출처, 작성자. 소요시간은 배정 계산용이며 의료적 사실과 구별한다.

추천 계획 기본값: 복약 챙기기 30분, 동행 120분, 약 수령 30분. 사용자가 수정할 수 있고 화면에 예상 소요시간으로 표시한다. 동행에는 사용자가 왕복 이동·대기를 포함할 수 있다. AI가 실제 이동시간을 안다고 가정하지 않는다.

반복은 매일·요일·종료일을 지원한다. 서버에서 앞으로 14일의 개별 발생 건을 만들어 배정하고 매일 다음 날을 추가한다. 종료일 미상 처방을 임의로 무기한 복약 지시로 만들지 않는다. 반복 규칙 수정은 이후 발생분에만 적용하며 각 발생 건은 별도로 완료·인계 가능하다.

### 7.1 일정 삭제

복약 일정 관리 on/off 설정은 제공하지 않는다. 일정 메뉴의 ‘삭제’를 사용하며 반복 일정이면 아래 두 선택지만 제공한다. 단발 일정에는 일반 삭제만 제공한다.

- ‘이번만 삭제’: 선택한 발생 건만 취소하고 이후 반복 일정은 유지한다.
- ‘앞으로 삭제’: 선택한 발생 건부터 같은 반복 시리즈의 이후 미완료 발생 건을 취소하고 해당 시점 이후 생성을 중단한다. 다른 처방·다른 반복 시리즈는 유지한다.
- 삭제 범위에 포함되는 예약 알림과 열린 인계 요청을 종료하고 배정 건수 계산에서 제외한다.
- 진료 요약·처방 기록과 이미 완료한 업무 이력은 유지한다. 기록 자체 삭제는 별도 기능이다.
- UI에서는 삭제로 표시하지만 서버에서는 취소·반복 중단 이력을 보존해 추출 작업 재시도나 반복 발생 작업이 같은 일정을 다시 만들지 않게 한다.
- 새 진료·새 처방에서 추출한 별개 일정은 생성할 수 있다. 관리 끄기 설정을 남겨 향후 전체 복약 일정을 막지 않는다.
- ‘내가 못함’은 인계, ‘이 일정이 필요 없음’은 삭제로 처리한다. 일정 삭제가 약 복용 자체를 중단하는 의미로 표시되지 않게 한다.

## 8. 개인 가능 시간

- 요일별 고정 근무시간을 입력한다. 날짜별 수정으로 예외를 반영한다.
- 날짜 시작과 끝을 탭해 범위를 선택하고 상태를 일괄 적용한다. 단일 날짜도 선택 가능하다.
- 미등록: 자동 배정 후보에서 제외.
- 불가: 그 날짜 배정 후보에서 제외.
- 풀타임 가능: 사용자가 정한 활동 시간 전체에 가능.
- 파트타임 가능: 활동 시간에서 근무시간과 날짜별 불가 구간을 뺀 시간에 가능.
- 활동 시간 추천 기본값은 07:00~22:00이며 수정 가능. 풀타임을 수면 시간까지 포함한 24시간으로 해석하지 않는다.
- 일정의 전체 예상 구간이 가능 시간에 들어와야 후보가 된다. 시작 시각만 가능하다고 배정하지 않는다.
- 같은 사람이 다른 공동체에서 맡은 일정과도 중복 배정하지 않는다. 다른 공동체 사용자에게 그 일정의 상세는 노출하지 않는다.

근무가 자정을 넘으면 날짜별 구간으로 나누어 계산한다. 개인 캘린더 전체 내용은 공유하지 않고 배정에 필요한 가능 여부만 제공하는 것을 기본으로 한다.

## 9. 담당자 배정 규칙 — 추천안

### 9.1 기본 원칙

가족 모두 우선순위를 바꿀 수 있고 동순위를 허용한다. 숫자가 낮을수록 우선한다. 1순위에 일이 몰리는 것은 허용한다. 순위 변경은 이후 신규 배정부터 적용하고 기존 배정을 조용히 바꾸지 않는다.

배정 순서: 전체 시간 가능 + 일정 충돌 없음 → 가장 높은 우선순위 → 배정 건수 적음 → 동률이면 가까운 관련 일정을 함께 처리할 사람 → 여전히 동률이면 고정된 구성원 ID 순.

건수 기준 추천: 해당 공동체에서 일정 날짜가 속한 월~일 주간의 미취소 배정 발생 건 수. 완료 건도 포함한다. 반복 업무는 각 발생 건을 1건으로 센다. 다른 공동체의 건수는 점수에 합하지 않되 충돌은 검사한다.

### 9.2 가까운 일정 묶기

하루 고정 담당 대신 같은 대상·같은 날의 가까운 업무를 한 번의 배정 단위로 묶는다. 일정 자체는 별개로 남는다.

1. 신규 배정할 일정을 시간순으로 정렬한다.
2. 시작 시각 차이가 첫 일정으로부터 240분(4시간) 이내인 업무를 묶음 후보로 본다. 연쇄적으로 하루 전체가 묶이지 않도록 첫 시각을 기준으로 한다.
3. 해당 업무들이 서로 겹치거나, 중간 대기 시간을 포함한 전체 구간에 가능한 사람이 없으면 나눠 배정한다. 다른 위치로의 이동 가능성은 보장하지 않으며 예상 시간 조정으로 반영한다.
4. 각 업무에서 가능한 최상위 순위 후보의 공통 집합이 있을 때만 묶는다. 묶기 때문에 더 낮은 순위에게 업무를 넘기지 않는다.
5. 묶음 처리 직전 건수로 후보를 비교한다. 전부 수행 가능한 최소 건수 후보가 있으면 한 명에게 묶음을 배정한다. 업무별 최소 건수 후보가 서로 다르면 묶음을 나눠 기본 순서를 지킨다.
6. 묶음 배정 후 건수는 실제 업무 수만큼 증가한다. 동률일 때 묶음 전체를 처리할 수 있는 사람을 우선하므로 첫 업무 후 건수가 증가했다는 이유로 다음 업무를 즉시 다른 사람에게 넘기지 않는다.

예: A와 B가 1순위이고 현재 주간 건수가 각 2건이며 13:00 복약 도움(30분)과 14:00 병원 동행(120분)을 둘 다 수행할 수 있으면 한 사람에게 두 업무를 배정한다. 13시~16시 중간 전체가 가능한지 검사한다. A는 13시만, B는 14시만 가능하면 각자 배정한다. A가 1순위, B가 2순위라면 묶음을 위해 1순위 가능한 업무까지 B에게 옮기지 않는다.

4시간 묶음 범위는 사용자 확정 사항이다. 주간 건수 기준은 추천 기본값이다. 4시간은 첫 업무와 마지막 업무의 시작 시각 차이이며 마지막 업무 종료까지의 총시간 상한이 아니다. 예를 들어 13시·17시는 묶음 후보지만 13시·17시 1분은 나눈다. 중간 간격이 각각 4시간 이내라도 첫 시각에서 4시간을 넘는 연쇄 묶음은 금지한다. 장소 최적화·이동 경로 계산은 MVP 범위가 아니다.

### 9.3 수동 수정과 시간 변경

표의 세로축은 날짜·시간순 건강 일정, 가로축은 가족 구성원이다. 각 행의 선택은 1명만 가능하다. 담당자를 바꾸면 기존 체크가 해제된다. 다중 동행자는 후속 범위다.

가능하지 않은 사람을 선택하면 충돌 내용을 보여주고 저장하지 않는다. 직접 맡으려면 해당 가능 시간을 먼저 수정한다. 미등록인 사용자도 자신의 가능 시간을 입력한 뒤 맡을 수 있다.

개인 가능 시간을 바꾸면 변경 후 충돌하는 미래 담당 일정만 담당자를 해제하고 인계 대기로 만든다. 나머지 일정은 유지한다. 기존 담당자와 변경 이력은 남긴다. 일정을 취소하지 않으며 다른 사람에게 자동 재배정하지 않는다. 순위 변경만으로 기존 일정 담당자를 해제하지 않는다.

## 10. 인계와 상태 모델

‘떠넘기기’는 기획 용어로 유지하고 실제 화면 버튼은 ‘다른 가족에게 부탁하기’를 추천한다. 받는 사람 버튼은 ‘내가 맡기’다.

| 상태 | 의미·가능 행동 |
|---|---|
| 확인 필요 | 추출된 필수 정보나 복약 내용 확인 필요, 자동 배정·해당 시각 알림 보류 |
| 담당자 없음 | 첫 배정 시 가능한 후보 없음, 가족에게 맡기 요청 |
| 배정됨 | 담당자 1명 존재, 완료·인계 가능 |
| 인계 대기 | 기존 담당자가 수행 불가. 담당자는 비어 있고 이전 담당자는 이력으로 표시 |
| 완료 | 업무 수행 기록 존재 |
| 기한 경과 | 미완료 상태에서 수행 구간·기한 경과. 담당자 유무와 이전 상태 함께 보존 |
| 취소 | 수행 불필요, 알림 중단 |

인계 요청 시 기존 담당자 해제와 인계 요청 생성, 가족 알림 생성이 같은 트랜잭션에서 처리된다. 당사자 화면에 ‘아직 맡은 가족이 없습니다’를 명시한다. 두 명이 동시에 수락하면 서버가 한 명만 성공시키고 다른 사람에게 이미 배정됨을 반환한다.

수락 시점에 다시 가능 시간·중복 일정을 검사한다. 과거 기한이 지난 일정은 그대로 수락하지 않고 시간을 수정하거나 결과를 기록하도록 안내한다. 기한이 지났다는 이유만으로 취소·완료되지 않는다.

반복 알림에서 말하는 대상은 ‘담당자 없는 일정’과 ‘인계 대기 일정’이다. 담당자는 있으나 아직 수행 전인 정상 일정과 구분한다. 확인 필요 기록도 인계 요청으로 취급하지 않는다.

## 11. 알림

- 필수: 실제 웹 푸시와 서비스 내 알림함. 푸시 권한 거부·미지원이면 화면에 안내하고 알림함은 유지한다.
- 이벤트: 진료 처리 완료, 신규 배정, 담당자 변경, 인계 요청·수락, 일정 도래.
- 담당자 없는 일정 반복 알림: 구성원별 ‘매일 받기 / 최초 1회만 받기’.
- 추천 발송 시각: 매일 09:00 KST, 아직 담당자 없는 미래 일정들을 하나의 알림으로 묶는다.
- 최초 1회는 각각의 인계 요청 또는 최초 미배정 발생 사건 기준이다. 새 인계 사건은 다시 1회 알린다. 단순 새로고침·작업 재시도는 새 사건이 아니다.
- 신규 요청일에는 최초 알림을 보냈으면 같은 날 정기 반복 알림에서는 제외한다. 수락·완료·취소 시 해당 반복 알림을 중단한다.
- 기한 경과 시 상태를 기록하고 1회 안내한 뒤 매일의 미래 일정 인계 알림에서는 제외한다. 홈의 기한 경과 목록에는 계속 남긴다. 이 정책은 추천안이다.
- 일정 도래 기본값: 시작 30분 전과 시작 시각. 급하게 생성돼 지난 알림 시각은 몰아서 발송하지 않는다.
- 알림 클릭은 해당 기록·일정으로 이동하며 서버가 다시 공동체 권한을 확인한다.
- 잠금 화면 푸시에는 약명·진단명을 쓰지 않고 ‘가족 돌봄 일정이 있습니다’처럼 최소 정보만 보낸다.
- 알림은 응급 대응이나 정확한 복약 전달을 보장하는 수단으로 표현하지 않는다.

## 12. 구현 구조

단일 Spring Boot 애플리케이션과 PostgreSQL로 시작한다. 서버에서 STT·문서 인식·구조화 요약 API를 호출한다. 별도 Python 서버, 마이크로서비스, Redis, Kafka는 MVP 필수로 두지 않는다.

작업은 DB 작업 테이블과 제한된 워커로 실행한다. 접수된 작업 ID를 반환하고 프론트가 처리 상태를 조회한다. 서버 재시작 시 미완료 작업을 회수하며 요약 결과 저장·일정 생성은 중복되지 않게 한다. AI 업체 키는 서버에만 둔다.

외부 모델은 한국어 녹음·약명·숫자 샘플로 10/2에 시험하고 선정한다. 최종 업체·모델·비용 상한·저장 정책은 아직 미정이다. 모델 학습용 의료 데이터셋 구축은 하지 않는다.

푸시는 표준 Web Push 방식으로 프론트 Service Worker와 서버 발송기를 연결한다. 알림은 DB Outbox에 먼저 남기고 재시도한다. 전달 요청 성공을 사용자가 확인한 것으로 기록하지 않는다. 만료 구독은 비활성화한다.

프론트는 Vercel, 백엔드 Spring Boot는 AWS EC2, PostgreSQL은 백엔드 인프라에서 관리한다. 프론트와 API는 서로 다른 HTTPS Origin이다. 문서는 비공개 저장소, 음성은 분리된 임시 저장소에서 관리한다. 의료 데이터 응답과 문서는 PWA 오프라인 캐시에 넣지 않는다.

### 12.1 Vercel 프론트 / EC2 API 분리 — 확정 배포 방식

| 요청 흐름 | 제공 주체 |
|---|---|
| Browser → `https://<frontend>.vercel.app` | Vercel이 프론트 화면 제공 |
| Browser → `https://<api-domain>/api/...` + Authorization: Bearer | 별도 HTTPS API → EC2 Spring Boot |
| Spring Boot → PostgreSQL | 백엔드 내부 DB 접근 |

- 주소는 자리표시자이며 실제 production URL과 API 도메인은 아직 미정이다. API 도메인은 가비아에서 관리할 계획을 유지한다.
- 프론트는 운영 API 기본 주소를 환경변수로 관리하고 그 주소와 `/api/...` 경로를 조합해 호출한다. 프론트 Origin의 상대 경로 `/api/...`를 EC2 API 호출 방식으로 사용하지 않는다. Vercel API rewrite/proxy를 새 요구사항으로 추가하지 않는다.
- Vite를 사용하는 경우에만 `VITE_API_BASE_URL=https://<api-domain>`을 구현 예시로 사용한다. 변수 이름·프레임워크는 최종 확정사항이 아니다. 이 예시의 base URL에는 `/api`를 넣지 않으며 요청 경로에 `/api/...`를 한 번 붙인다. 프론트에 노출되는 API 주소는 비밀 값이 아니며 AI 키·DB 비밀 값은 프론트 환경변수에 넣지 않는다.
- Nginx는 EC2 API의 HTTPS reverse proxy로 사용할 수 있는 추천 구성이다. API의 `/api/` 접두사를 유지해 Spring Boot로 전달하고 업로드 제한을 맞춘다. Nginx가 프론트 정적 파일이나 SPA fallback을 제공해야 한다는 전제는 제거한다.
- 추천 구성에서 Spring Boot 내부 포트와 PostgreSQL은 인터넷에 직접 노출하지 않고 API HTTPS 진입점만 공개한다. API DNS를 EC2의 고정 공개 IP(Elastic IP 권장)에 연결하고 인증서를 설정한다. 실제 호스트·IP·인스턴스 사양·예산은 배포 작업에서 확정한다.
- SPA 새로고침 fallback·프론트 정적 캐시·PWA Service Worker 업데이트는 Vercel 프론트 배포에서 확인한다. Service Worker와 Web Push 구독은 프론트 Origin에 속하며, 구독 등록·알림 조회 API는 Bearer/CORS 계약을 따른다. 푸시 클릭은 프론트 화면으로 이동하고 로그인/권한 확인 후 데이터를 조회한다. Origin이 바뀌면 기존 푸시 구독을 그대로 사용할 수 있다고 가정하지 않는다.

### 12.2 프론트·백엔드 배포 흐름

- 프론트: Vercel의 배포 흐름을 사용한다. Git 연동 자동 배포는 추천 구현이며 production 브랜치·빌드 명령·출력 디렉터리·환경별 API 주소를 연결 시 고정한다. preview 배포가 생겼다는 사실만으로 EC2 CORS 허용 목록에 자동 추가하지 않는다. 프론트 산출물을 EC2에 전송하거나 SSH로 정적 파일을 교체하는 절차는 사용하지 않는다.
- 백엔드: 기존 GitHub Actions → 빌드·필요 검사 → Docker 이미지 생성 → EC2 버전 교체 → 상태 확인 흐름을 유지할 수 있다. 실패 시 이전 이미지로 복구하며 DB 마이그레이션은 이전 앱과의 호환성을 고려한다.
- SSH 키·AI 키 등은 저장소 코드에 포함하지 않는다. 워크플로 비밀 값과 서버 런타임 값을 분리한다. Vercel의 공개 프론트 환경변수에 토큰·서버 키를 넣지 않는다.
- 각 배포 서비스의 배포를 직렬화하고 버전을 기록한다. 독립 배포라도 API 호환성이 깨지는 변경은 순서를 조율한다. 단일 백엔드 인스턴스 교체의 무중단은 보장하지 않는다.

분리 배포는 확정사항이다. EC2 내부 실행·저장소·Nginx·Vercel Git 연동·워크플로 세부 구성은 추천안이며 실제 설정·배포는 별도 구현 작업이다. [9][10][11][12]

### CORS·Cookie·CSRF 구현 경계 — 확정

Vercel 프론트가 별도 EC2 API Origin을 직접 호출하므로 서버에서 CORS를 설정한다. CORS는 브라우저의 교차 출처 접근 정책이며 토큰 인증·공동체 인가를 대신하지 않는다.

| 구분 | 정책 |
|---|---|
| 운영 허용 Origin | 실제 Vercel production origin만 허용하는 것이 기본. 필요하면 명시적으로 등록한 preview origin 추가 |
| 개발 허용 Origin | localhost 프론트 개발 origin을 별도 등록. 포트는 프론트 환경 확정 후 설정 |
| 금지 기본값 | 운영에서 `*` 전체 허용 또는 모든 vercel.app preview 일괄 허용을 기본으로 사용하지 않음 |
| 메서드 | 실제 API에 필요한 메서드만 허용. preflight OPTIONS 처리를 지원 |
| 허용 헤더 | Authorization, Content-Type, Idempotency-Key 및 실제 명세에서 요구하는 추가 헤더만 허용 |
| 인증 Cookie | 자동 전송하지 않음. Cookie 인증용 credentials: include 및 Access-Control-Allow-Credentials 설정을 요구하지 않음 |

Authorization 헤더, JSON Content-Type, Idempotency-Key 등으로 preflight가 발생할 수 있다. OPTIONS는 Bearer 토큰 제출 없이 허용 Origin·요청 메서드·헤더를 검증해 처리하고 실제 API 요청에는 인증·인가를 수행한다. Spring Security 인증 필터보다 CORS/preflight 처리를 먼저 적용하고 허용 Origin의 401/403 응답에도 필요한 CORS 응답 헤더가 붙도록 한다. 여러 Origin을 처리할 때 Vary: Origin을 고려한다. 프론트는 인증 Cookie가 아닌 명시적 Authorization 헤더를 사용하며 fetch의 credentials: omit을 구현 예시로 사용할 수 있다.

Cookie SameSite·Secure/HttpOnly Cookie 전달·Cookie 기반 CSRF 토큰을 현재 인증 흐름의 요구사항으로 두지 않는다. 브라우저가 인증 토큰을 Cookie로 자동 첨부하지 않는 이 Bearer 경로에는 기존 Cookie 세션용 CSRF 설명을 적용하지 않는다. 애플리케이션의 다른 기능에서 Cookie 인증 등을 추가하면 그 경로의 CSRF 위험과 방어를 별도로 검토한다. ‘CSRF가 절대 필요 없다’고 일반화하지 않는다.

## 14. 녹음·건강정보 관련 검토

이 절은 2026-10-02 확인한 공식 자료를 바탕으로 한 설계 검토이며 서비스의 적법성 확정 의견은 아니다.

- 녹음을 바로 삭제하면 합법이 된다는 규칙은 없다. 통신비밀보호법은 공개되지 않은 타인 간 대화 녹음 등을 제한한다. 대화 참여자의 녹음에 관한 판례와 별개로 저장·공유·서비스 제공에는 다른 쟁점이 남는다.[1][2]
- 건강정보는 개인정보 보호법상 민감정보에 해당하며 적법한 처리 근거, 별도 동의가 필요한 경우의 동의, 안전조치를 검토해야 한다. 가족 공유의 범위·수신자, 외부 AI 처리위탁·국외 이전 해당 여부도 확인한다.[3][4]
- 전사·요약·문서도 여전히 개인정보일 수 있으므로 음성 삭제만으로 개인정보 처리가 끝나지 않는다. 임시 음성, 전사, 문서, 백업, 로그, 외부 업체 보관을 각각 정의한다.
- 추천 데이터 보관: 음성은 전사 저장 후 즉시 삭제, 실패 음성 최대 24시간. 전사·요약·문서는 사용 목적과 고지된 보유기간 내 관리하며 기록 삭제 요청 시 연결 파일·데이터도 삭제한다. 백업 만료·업체 보관은 운영 정책에서 별도로 고지한다.
- 실제 데이터를 처리하는 공개 운영 전에는 동의·처리방침·계정 보안·접근 통제·AI 업체 조건을 갖춘다. 핵심 기능 시연 배포와 실제 의료정보를 받는 운영을 구분한다.

### 14.2 이번 시연의 확정 운영 조건

- 10/9 배포는 가상 진료 데이터 시연이다. 실제 어르신의 진료 녹음·처방전·환자 개인정보를 받는 운영은 이번 범위에서 제외한다.
- 완전 창작 대본과 문서를 사용하고, 팀원이 대본을 읽는 경우 녹음·AI 전송·시연 사용에 동의한 사람만 참여한다. 가상 진료 내용이어도 사람을 식별할 수 있는 목소리나 실제 계정 정보는 별도로 고려한다.
- 이름·전화번호 조회는 시연용 사전 등록 데이터로 제한하고, 임의의 실제 사람을 조회하는 기능으로 운영하지 않는다. 시연용 번호로 전화·문자를 보내지 않는다.
- 공개 진입 화면에 ‘가상 데이터 시연용’을 표시한다. 일반 방문자는 준비된 샘플로 체험하고, 자유 녹음·파일 업로드는 팀의 시연 세션에서만 허용한다. 이는 실제 데이터 유입을 막기 위한 추천 운영 방식이다.
- 실제 푸시에 사용하는 기기 구독 정보·접속 로그도 목적에 필요한 범위로 관리한다. ‘가상 데이터이므로 개인정보가 전혀 없다’고 표현하지 않는다.

PRD·발표에 사용할 수 있는 문장: “본 MVP는 가상 진료 데이터로 녹음·요약·가족 일정 분담 흐름을 시연한다. 대화 참여자의 녹음에 관한 판례와 개인정보 보호법의 처리·공유·파기 원칙을 참고해 설계했으며, 실제 건강정보 운영 전 필요한 동의·접근 통제·외부 AI 처리 조건을 별도로 적용한다.”

## 15. 개발 일정·담당

## 16. MVP 수용 기준

1. 어르신과 가족이 같은 화면에서 각각 녹음하고 올바른 대상에게 기록을 저장한다.
2. 녹음 사용 확인 후 추가 전사 승인 없이 처리가 시작되고 진료별 상세를 볼 수 있다.
3. 전사 저장 후 서버 원본 음성이 삭제되고 요약 실패 재시도는 전사로 가능하다.
4. 문서의 명확한 정보는 추출되고 숫자·날짜 누락·소스 충돌은 확인 필요로 남는다. 약 신규·변경 확인 정책을 검증한다.
5. 미등록·불가·근무 시간·기존 일정 충돌 후보는 자동 배정되지 않는다.
6. 1순위 2명·2순위 1명 사례에서 최상위 가능 순위와 건수 규칙을 지킨다.
7. 13시·14시 묶음 사례, 4시간 경계(포함)·4시간 초과(제외), 연쇄 묶음 금지, 시간 일부만 가능한 반례가 기대대로 배정된다.
8. 표에서 담당자 1명만 선택되며 모든 가족이 우선순위를 변경할 수 있다.
9. 가능 시간을 줄이면 충돌하는 미래 일정만 인계 대기가 된다.
10. 두 가족이 동시에 ‘내가 맡기’를 눌러도 최종 담당자는 1명이다.
11. 매일/최초 1회 옵션, 요청별 중복 방지, 수락 시 반복 중단을 확인한다.
12. 실제 iPhone PWA와 Android에서 서비스를 닫은 상태의 푸시 수신·상세 이동을 확인한다.
13. 다른 공동체의 ID로 기록·파일·일정을 조회하거나 수정할 수 없다.
14. 작업 재시도·서버 재시작으로 일정과 알림이 중복 생성되지 않는다.
15. 기한이 지나도 미수행 일정이 자동 완료되거나 삭제되지 않는다.
16. 복약 수행 방식 선택 UI·필드와 공동체 복약 관리 on/off 설정이 없으며 반복 일정은 이번만/앞으로 삭제할 수 있다.
17. 앞으로 삭제는 선택한 반복 시리즈의 미래 미완료 업무·인계·알림을 종료하고 진료·처방·완료 이력을 유지한다. 다른 시리즈에는 영향이 없고 재처리로 취소 일정이 되살아나지 않는다.
18. 신규·변경 복약은 한 화면에서 확인하며 이미 확인된 처방을 매 복용 때 재확인하지 않는다. 모호한 값·충돌만 필요한 입력으로 해결한다.
19. Vercel 프론트에서 환경변수의 별도 EC2 HTTPS API로 Bearer 요청이 동작하고 Vercel 프론트 배포·GitHub Actions 백엔드 배포 및 실패 복구를 확인한다.
20. 토큰 없음·잘못된 토큰·만료·revoked는 401, 다른 공동체·LEFT 멤버는 403이다. 로그아웃 후 현재 토큰 재사용은 거부되고 다른 기기 세션은 유지된다.
21. 운영 허용 Origin의 preflight·Authorization/Content-Type/Idempotency-Key 요청과 401/403 응답을 확인한다. 미등록 Origin은 CORS 허용하지 않는다. CORS 거부와 서버 인가를 별도로 검증한다.
22. 문서 원본·진료 요약·처방·일정·인계·공동체의 UUID를 바꿔도 타 공동체 접근이 거부된다. 다른 사용자 알림·구독·개인 설정 소유권도 확인한다.

23. 문서의 10MB/10페이지/10장 경계, 위장 MIME·손상 파일, 동시 이미지 추가를 검사하고 거부 입력에 OpenAI가 호출되지 않는지 확인한다. 외부 입력 제한 오류는 실패 단계·코드·조정 안내로 표시한다.

평가용 입력은 가상 진료 대화·문서를 사용한다. 명확한 지시, 날짜 없음, 약 용량 충돌, 소음·인식 실패, 조건부 지시, 중복 업로드 사례를 포함한다. 데모 성공과 의료적 정확도 검증을 동일시하지 않는다.

## 17. 후속 개발

1. 정식 가입: 전화번호 인증, 이름, 실사용 동의, 비밀 초대 코드, 탈퇴·공동체 접근 관리.
2. 이웃 도움: 모든 가족이 처리하기 어려운 식사·청소·빨래·동행을 근처 이웃과 연결. 신원·비용·책임·취소 정책을 별도 PRD에서 정의하고 진료 원문을 이웃에게 기본 공개하지 않는다.
3. 약통: ESP32/Arduino가 감지한 열림 이벤트를 서버로 보내고 어르신에게 복용 여부를 질문한다. 열림 자체는 복용 완료가 아니다. 어르신 응답을 복용 기록에 반영하고 가족 도움 업무 완료와 별도 데이터로 둔다. 센서 종류는 시제품 검증 후 정한다.

## 18. 남은 결정

- 프론트 팀의 React 사용 여부·빌드 도구 최종 확인. JavaScript·PWA 방향과 임시 서비스명 ‘가족 돌봄 서비스’는 반영.
- 주간 배정 건수 비교 기준 확인. 묶음 범위 4시간은 확정.
- 단순 확인 UI의 구체 문구·일괄 확인 범위는 본 초안대로 구현하는 추천. 사전 등록 4계정·Bearer 인증은 확정이며 세션 수명은 추천 기본값.
- 실제 Vercel production URL·명시적 preview Origin 목록, 실제 API 도메인, EC2 사양·예산, 배포 브랜치·저장소 구성, 프론트 환경변수 이름·개발 포트, AI 공급자·비용·보관 조건. Vercel 프론트·EC2 백엔드 분리 배포는 확정.
- 브라우저 토큰 저장 방식은 최종 미정. localStorage는 가상 데이터 MVP 추천안이며 실제 건강정보 운영 정책은 후속 검토.
