# 공개 모의 진료 요약 평가 — 운영 승격 보류

2026-10-09 KST. 가이드라인 0.3.0 규칙 → 후보 v1.2/v1.3/v1.4. 최종 문서 상태 0.3.1. 번역·의미 평가는 Codex AI의 원문 대조 초안이며 사람 개발자 승인·의료진 검증 전이다.

## 결론

자료 준비, 실행 코드 공통 경로 분리, 비용 제한 평가기, 로컬 테스트와 실제 API 평가는 수행했다. 그러나 **품질 개선 성공 또는 검증 완료로 판정하지 않는다. 신규 프롬프트를 운영 기본값으로 승격하지 않았다.**

개발 6건에서 후보 v1.3의 서버 파싱 통과는 동일 출력 순서의 v1.1 대비 2→4건이었지만, 근거와 주장 불일치가 남았다. 합성 회귀에서 이전 통과 사례가 실패했고, 별도 평가 4건 중 1건만 파싱됐으며 그 결과도 의미 근거 검토에서 실패했다. 따라서 프롬프트 v1.1과 원래 출력 순서를 유지한다. 현행 v1.1도 이 공개 긴 대화 세트에서 안전성 입증된 것은 아니다.

## 실행 경로와 변경 위치

- `OpenAiProcessingAdapter.analyze` → `analysisRequest` → `requestAnalysis`(`/v1/responses`) → `parseAnalysis` → `AnalysisOutputValidator.validate`가 실제 경로다.
- 사용 모델: **gpt-5.4-mini-2026-03-17**. 모델 교체·파인튜닝 없음. `store=false`, developer 지침/user 서버 컨텍스트 분리, strict JSON schema, `max_output_tokens=12000`. temperature/reasoning은 기존처럼 명시하지 않았다. 응답상 reasoning tokens는 전 호출 0, service tier는 default였다.
- 기존 v1.0/v1.1 파일과 작업 중인 변경·문서 삭제 상태를 보존했다. 신규 v1.2~v1.4는 실호출했지만 채택하지 않은 후보다. 모델에 전체 가이드라인·평가표·진료 기록 note를 보내지 않았다.
- 코드 변경: 요청 구성·통신·파싱을 작은 공통 메서드로 분리, 응답이 출력 상한에 닿으면 완료 상태라도 `AI_OUTPUT_INCOMPLETE` 처리, 활성 버전에서 프롬프트 경로 생성. 기본 프롬프트 및 일정/처방 적용 정책은 그대로다.
- 근거를 먼저 생성하는 JSON **필드 순서만** 변경한 실험도 수행했다. 필드/타입/required는 동일함을 단위 테스트로 확인했다. 이 순서도 운영 기본값에는 적용하지 않았다. 평가기만 명시적으로 해당 순서를 선택한다. 동일 순서의 v1.1을 새로 실행하여 v1.3과 비교했다.
- 실제 결과는 워커가 revision의 summary/details/evidence와 후보로 저장하고 서비스 DTO로 전달한다. 프론트 `21_Hungry_FE/src/pages/record-audio-analysis/RecordAudioAnalysisPage.jsx`는 `summary.text` 및 details를 표시한다. 이 흐름은 소스 확인이며 브라우저·운영 DB E2E 검증이 아니다. FE 변경 없음.
- DB 없는 `SummaryEvaluationMain`은 위 동일 요청/통신/파싱 메서드를 직접 사용한다. Spring/Repository/Worker를 시작하지 않고 운영 진료 기록·처방·돌봄 일정을 만들지 않는다. PRD/API/DB 계약 변경 없음.

### 관찰된 실패와 수정 이유

- v1.2: day3_consultation08의 가래 질문 뒤 정정을 반영하지 않음, 06/04의 태그를 삭제한 가짜 인용, 02/05의 질문 단독 근거·근거 번호 이동. 전체 대화 읽기, 질문+답변, 역할, 정확 인용, 비행동 TASK 금지 규칙을 추가했다. 6건을 다시 실행했으나 채택 기준 미달이었다.
- v1.3: 같은 문제가 지속되어 근거를 먼저 출력하고 온전한 발화를 복사하도록 했다. 기준도 같은 출력 순서로 재실행했다. 원문 인용 형식은 일부 나아졌지만 **배열 안에 존재하는 엉뚱한 근거 번호**가 남았다. 가래 정정은 이 샘플에서 고쳤지만 약·검사·주의사항의 의미 근거 실패가 개선을 상쇄한다.
- v1.4: 중복 규칙을 줄인 한국어 지침, 1~2개 증상 묶음, 불필요한 근거 감소를 시도했다. 6건 재평가에서 가래 오류가 다시 생기고 5건이 파싱 실패했다. 채택하지 않았다.
- 합성 회귀 H01: 기존에는 정확했던 정정 인용에 v1.3이 존재하지 않는 `의사:` 접두어를 넣어 전체 응답이 거절됐다. D04는 원문에 없는 “확정된 치료나 약 처방은 없음”을 추가했다. D07의 필요 시 약은 텍스트에 조건이 있지만 item의 `isConditional=false`였다. 약은 여전히 사용자 확인 대상으로 처리되어 자동 적용되지는 않았다.

가이드라인에는 일반화 가능한 규칙과 짧은 가상 예시만 반영했다. 공개 대화 전체나 평가 정답은 프롬프트/MD에 넣지 않았다. v1.3은 `candidate-freeze.json` 해시로 고정한 **진단용 최종 후보**이며 승인된 후보가 아니다. 별도 평가 응답을 본 뒤 프롬프트를 수정하지 않았다.

## 비용·출력 한도·재현

[OpenAI 공식 모델 요금](https://developers.openai.com/api/docs/models/gpt-5.4-mini)을 2026-10-09 확인: 입력 $0.75/M, 캐시 입력 $0.075/M, 출력 $4.50/M. 총 입력 204,006토큰(캐시 108,544 포함), 출력 82,853토큰(추론 0), 예상 **$0.4525758**. 실패 및 번역 수정 전 호출도 포함한다. 실제 청구서·세금과 다를 수 있다.

호출 전 `2 × ((요청 UTF-8 byte 수 + 4096) × 입력 단가 + 12000 × 출력 단가)`를 예약하고 누적 예약/비용과 다음 호출을 더해 $3 이하인지 검사한다. 캐시 절감은 선반영하지 않는다. 입력 크기·출력 상한과 예상치보다 비싼 tier 여유를 포함했다. 응답 usage가 없거나 중단되면 예약 금액을 유지한다. 잠금과 원자적 기록으로 중복 실행/중단 시 예산 손실을 방지한다. 자동 재시도 없음. 크레딧 소진이 아니라 개선 정체·회귀가 종료 사유다.

실제 최대 출력은 3,499토큰으로 12,000 상한 이내였고, 관찰된 incomplete/상한 도달은 0건이다. 평균 호출 7.87초, 최대 17.20초(요청 단위 시간). 같은 입력·프롬프트·모델·설정·schema 순서는 SHA로 재사용하며 실패도 몰래 다시 호출하지 않는다. 반복 샘플을 뽑아 가장 좋은 결과를 선택하지 않았다. 번역/채점/음성 전사 API 호출 없음.

## 재실행 명령과 관리

```powershell
.\gradlew.bat test --tests '*OpenAiProcessingAdapterTests' --tests '*AnalysisOutputValidatorTests' --tests '*AiContractResourceTests' --tests '*SummaryEvaluationTests'
# 실제 호출 없이 요청 준비/기존 결과 재사용 확인 (실패 기록은 exit 1)
.\gradlew.bat summaryEval '-PevalSet=development' '-PevalPrompt=1.3'
# 명시적 실제 호출 opt-in; 이미 같은 결과가 있으면 과금 없이 재사용
.\gradlew.bat summaryEval '-PevalSet=development' '-PevalPrompt=1.3' '-PevalLive=true'
.\gradlew.bat summaryEval '-PevalSet=synthetic' '-PevalPrompt=1.3' '-PevalLive=true'
.\gradlew.bat summaryEval '-PevalSet=holdout' '-PevalPrompt=1.3' '-PevalLive=true'
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/report-summary-eval.ps1
```

평가기는 근거 우선 순서를 명시적으로 쓰며 운영 기본 순서와 다르다. **현재 운영과 완전히 같은 구성의 기준은 최초 v1.1 6건**, v1.3에 대한 순수 프롬프트 비교 기준은 같은 순서로 재측정한 v1.1 6건이다. 두 기준을 합쳐 단일 개선율을 주장하지 않는다.

이후 수정은 새 프롬프트 버전 파일 + 가이드라인 버전 + 변경 근거 사례 ID를 남기고 개발/합성 전체를 재실행한다. 실패를 숨기기 위해 원본 응답·ledger를 지우지 않는다. 모델/설정 변경은 별도 비교 작업으로 승인받는다. 이번 별도 평가를 보고 새 규칙을 만들면 해당 4건은 개발 세트로 편입하고 새로운 미사용 평가 사례를 확보한다. 운영 의료 데이터는 이 평가 디렉터리에 넣지 않는다.

## 서버 반영

커밋·푸시·배포는 실행하지 않았다. 새 프롬프트는 **승격 보류**이므로 이번 작업을 “요약 품질 개선 배포 준비 완료”로 올리면 안 된다. 평가 도구와 출력 한도 오류 처리만 검토해 반영할 수 있다.

승격하려면 원문/번역 사람 검토, 근거 의미 오류와 합성 회귀 해결, 새 별도 세트 검증을 먼저 해야 한다. 승인된 버전만 `ANALYSIS_PROMPT_VERSION` 및 요청 순서 선택에 반영하고 활성 경로 테스트를 갱신한다. 이후 통합 테스트·`bootJar`/이미지 빌드 → 기존 CD로 배포 → 비식별 합성 입력으로 새 job의 모델/프롬프트 버전·요약 표시·확인 정책 확인 순서다. DB migration/FE 계약 변경은 필요 없다. 기존 저장된 요약은 자동으로 새 프롬프트로 바뀌지 않으며 별도 사용자 요청 없는 운영 재분석은 하지 않는다.
